# Issue #8 — Adopt `/bootstrap-workflow-dispatch` from the donor repo

Issue: https://github.com/vzakharov/agent-project-boilerplate/issues/8
Export: `docs/issue/8/issue.md`

## Finding that changes the issue's framing

**The donor skill is not what the issue describes.** I read it out of
`Playgramai/playgramapp` (see "How the donor was read" below). Issue #8's
rationale says it is a general *"dispatch this workflow against this branch and
report back"* routine, useful *"for dispatching arbitrary GitHub Actions
workflows, not only test workflows."* It is not. It is a **narrow one-shot
workaround** for a single GitHub quirk:

> GitHub does not expose a brand-new `workflow_dispatch` workflow to
> `gh workflow run` until Actions metadata has seen it once. Before merge the
> default branch still points at the old workflow set, so a feature branch gets
> `HTTP 404: workflow <file>.yml not found on the default branch`. The fix is to
> add a temporary `push` trigger scoped to the current branch **and** the
> workflow file's own path, push it (one non-dispatch run registers the
> workflow), retry the real dispatch, then delete the temporary trigger.

Four steps, ~70 lines, no polling, no reporting, no test buckets.

I also checked whether the general-dispatch skill the issue describes exists
elsewhere in the donor. It does not. The donor's other unadopted skills are
`autopilot`, `explore`, `fix-ci`, `roundtable`, `synthesize`, `update-docs`,
`update-tests`, `weigh` — and `fix-ci`, the only other CI-shaped one, is
stack-bound triage (it shells out to a donor script and reads downloaded
Playwright artifacts), not a dispatcher. The name most likely got conflated in
recollection.

**This does not change whether to adopt it.** The skill is single-file, fully
generic, and solves a real quirk that bites exactly when an adopter of this
boilerplate first adds a dispatch-only workflow. Every acceptance criterion on
#8 is about adopting *this* skill, and all five are satisfiable as written. So:
adopt it, and correct the rationale rather than the deliverable.

## How the donor was read

Worth recording, because the issue's step 1 asserted this was impossible from
here — *"it is private, so this needs a session scoped to it — the file cannot be
read from here."*

`add_repo` does refuse: cross-owner adds are unsupported in this harness
version, so `Playgramai/playgramapp` cannot be attached to a session whose
sources are under `vzakharov`. But `$GH_TOKEN` in this environment already
carries access to it, so the Contents API reads the file directly with no clone
and no second session:

```bash
gh api "repos/Playgramai/playgramapp/contents/.claude/skills/<name>/SKILL.md" \
  --jq '.content' | base64 -d
```

That is worth knowing for the next cross-repo adoption: `/sync-upstream`'s full
clone is the right tool for triaging a range of commits, but reading one named
file needs neither a clone nor a differently-scoped session.
