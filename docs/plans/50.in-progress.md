# #50 — a skill for the template-fork path

Issue export: `docs/issue/50/issue.md`.

A fresh template fork arrives carrying every skill except the one that turns it
into a project. This adds that skill, and fixes the six places the by-hand run
behind the issue found the procedure **incomplete** rather than merely manual.

The skill is named **`/detemplate`**, it **deletes itself** as its last act, and
it **recognizes a fork nobody has detemplated** when a session there is asked to
build something instead. See § "Resolved"; one question remains open, carrying a
recommendation the plan is written with in force.

## 1 — `.claude/skills/detemplate/SKILL.md`

**Invocation:** `/detemplate <what we're building>`, or the recognition path in
§ 2a, which reaches the same place from a build request in a tree nobody has
detemplated. The brief fills `CLAUDE.md`'s "About this project" stub and drives
the group decisions; with no brief, ask for it.

**It routes through `/plan` and writes no source itself** — the issue settles
this, and the evidence is the run behind it: the plan caught #49 before anything
was deleted. So the skill's own end state is `/issue`'s: a plan file published
as a draft PR, and a copyable `/go <branch>`. Its shape follows from that — a
research half that decides, and a specification of what the plan must contain so
`/go` executes it in the right order.

### Step 0 — refuse where it does not apply

The guard is § 2a's predicate, and it refuses in **both** directions:

- **No `docs/catalog.md`** → not an unpruned fork. An adopted repo wanting a
  sibling wants `@.claude/skills/spinoff/SKILL.md`; a repo that already ran this
  has nothing left to strip.
- **Catalog present but `origin` names the boilerplate** → this *is* the
  boilerplate, and the operation is a fork, not a prune. Point at the template
  button. Catalog-presence alone would let a session delete this repo's own
  inventory, so the origin clause is load-bearing rather than a nicety.

This is `/spinoff`'s guard read backwards, and the two partition cleanly on the
same signal — which is why § 2a's split of `/spinoff`'s refusal message and this
step are one decision, not two.

### Step 1 — profile the fork; do not interrogate the operator

`ADOPTING.md` § Step 2's principle, minus the parts a whole-tree fork settles for
free (nothing to clone, no existing `.claude` to merge with). What still needs
probing: the trunk, whether any workflow runs, whether work is tracked as
issues, and the stack — including "no stack yet", which is the normal state of a
fork taken to start a project and the state finding 5 exists for.

What the tree cannot answer, asked as numbered prose in the plan turn: the
deploy path, visual surface, deployed logs, production datastore and numbered
migrations that decide the individual G6 rows.

### Step 2 — read the catalog into the plan, *before* anything is deleted

The catalog is deleted in execution (Step 5) and is the input to every group
decision, so the plan file records the decisions with their criteria attached
rather than citing a file that will not exist when `/go` runs. Read § "Reverse
closure" (new, item 5) in the same pass and record the edits each dropped group
costs.

This read-then-delete ordering is what routing through `/plan` buys, and it is
worth stating in the skill as the reason.

### Step 3 — derive the watermark, which git cannot give you

**Finding 3.** A template fork's single commit has no ancestry in the source, so
`git rev-parse HEAD` in a clone — `ADOPTING.md`'s recipe — is a clone a template
forker never made. Derive it instead by matching the source's commit list
against the fork's creation time:

```bash
gh api repos/<owner>/<fork> --jq .created_at
gh api repos/vzakharov/agent-project-boilerplate/commits --paginate \
  --jq '.[] | [.sha, .commit.committer.date] | @tsv'
```

The newest source commit at or before the fork's `created_at` is the mark.

**Finding 4.** `lineage` is written in the same breath:
`[{ "repo": "vzakharov/agent-project-boilerplate", "atSha": <the same sha> }]`.
The two fields start equal and diverge on the first sync — per
`@.claude/skills/sync-agent-infra/SKILL.md` § "The watermark", `lastSyncedSha`
advances and `lineage[0].atSha` never moves — and that first sync is what
overwrites the only other trace of the birth point. A watermark written without
it loses the birth point permanently.

### Step 4 — what the plan must contain

Per-group keep/drop with the criterion that decided it; the G6 rows as
hydrate-now-or-delete; the reverse-closure edits; the derived watermark; the
`CLAUDE.md` brief; the `vet.sh` disposition; and the deletion list.

2. The rest of the never rows: `README.md` (replaced, not merely deleted),

3. Prune the groups, applying the reverse-closure edits recorded in the plan.
4. Fill `CLAUDE.md`'s stub — which retires § 2a's standing notice along with it
   — and delete its § "Git conventions" adopter-inverts rule, which that rule
   instructs adopters to delete.
5. Write the watermark and clear both of the sync skill's stub markers.
6. `scripts/vet.sh`: leave the exit alone where the fork has no stack yet, and

## 2 — the vet contract admits a repo with no stack yet

**Finding 5, reduced.** The shipped `scripts/vet.sh` already exits `0`, so a
fresh fork that leaves it alone behaves correctly. Nothing is broken at
runtime. What is wrong is that **four places instruct an adopter to break it**,
stating the rule with no exception for a repo that has no stack to check:

- `scripts/vet.sh:5` — "In your repo this file exits `1` until they are wired in"
- `CLAUDE.md` § "Vetting" — "In an adopting project this file exits `1` until it
  runs that project's real checks"
- `ADOPTING.md` § "Implement `scripts/vet.sh`" — the same sentence
- `docs/catalog.md`'s `rewrite` bullet — the same again

An agent detemplating a stackless fork and following that literally sets `exit
1`, and then every prose-only PR fails step 1 of `/finalize` — which trains the
loop to route around the vet run, on a repo whose first several PRs are all
prose.

**The fix is prose, not machinery.** The rule gains its missing clause: a repo
with **no stack yet** legitimately exits `0` — the two built-in checks are the
whole run and they genuinely pass — and `exit 1` is for a repo whose stack is
present and unchecked. Wiring `scripts/vet.sh` is what you do when a stack
lands, alongside `.claude/hooks/session-start.sh`'s dependency install, which
`CLAUDE.md` § "Vetting" names as the paired site because nothing else does.

A `vet.sh` that self-armed on a stack manifest was considered and dropped: the
"is it wired?" test has no honest cheap form. A sentinel comment at each site
measures compliance with the sentinel convention rather than with wiring —
false-failing on a properly wired `vet.sh` whose author skipped the marker, and
false-passing on a marker with nothing behind it.

**One consequence to settle** (§ "Open questions" 1): `@.claude/skills/spinoff/SKILL.md`
Step 4 **asserts** that `scripts/vet.sh` exits non-zero on the seeded `main`,
and that `main` deliberately has no stack. Under the clarified rule it is
asserting the wrong thing.

## 2a — the skill recognizes a fork nobody has detemplated

A session that opens in a fresh fork and is asked to build a feature should say
so and route to `/detemplate` first, rather than building product code on top of
the template's inventory.

**The signal already exists**: `docs/catalog.md` present **and** `origin` not
naming the boilerplate. Catalog-presence alone is what `/spinoff` refuses on and
what Step 0 above refuses the *absence* of; the origin clause is what separates
the boilerplate itself — where no notice is wanted — from an unpruned fork.

Two surfaces carry it, because they catch different moments:

- **The skill's frontmatter `description`** names the situation and not only the
  command, so an ordinary build request in such a tree matches it.
- **`CLAUDE.md`'s "About this project" stub** carries the standing instruction:
  while this stub is unfilled and the tree still has the catalog, the first task
  is `/detemplate`, whatever was asked. It is always-loaded, so it reaches every
  session — and the detemplate run rewrites that very stub, so the notice
  removes itself with no separate cleanup step.

`@.claude/skills/spinoff/SKILL.md`'s refusal message splits to match: pointed at
the template button when the caller **is** the boilerplate, and at `/detemplate`
when it is an unpruned fork.

**Every mention of the skill is a bare name, never an `@`-reference.** The skill
deletes itself, so an `@.claude/skills/detemplate/SKILL.md` anywhere would
dangle afterwards and fail `check-skill-catalog.sh` assertion 1 — in the tree of
whoever just ran it. This is the same property that makes `/test-on-gh`'s
bare-name mentions correct to leave alone (§ "Reverse closure").

## DRY notes

**The template-fork procedure gets one home, and it is the skill.** Today it is
`ADOPTING.md` § "Template fork"; leaving it there and adding a skill that reads
it creates exactly the two-homes drift `CLAUDE.md` § "Writing things down"
names. The section becomes a pointer. Which of the two is the home is settled by
audience: `ADOPTING.md` is read **over the network, from a clone, by a session
that has none of these skills**, and its subset path must stay whole for that
reader; the template-fork path is read **in-tree, by a session that has every
skill**, so a skill is its natural home and a pointer covers the reader who
arrives at `ADOPTING.md` by mistake.

**The shared tail stays in `ADOPTING.md`; the skill restates only what actually
differs.** Three of its five steps have a materially different fork form — the
watermark SHA has no clone to read (finding 3), `vet.sh` takes the third state
rather than the adopter's `exit 1`, and the catalog-delete ordering has no
subset analogue at all. Those are new content, not copies. The two that are
identical — hydrate-or-delete G6, and `CLAUDE.md`'s stub — get one line each
pointing at the catalog rows the skill has already read. Forcing the differing
three into a shared statement would produce a paragraph hedged for two readers
and precise for neither.

**Reverse closure is inventory knowledge, so its home is `docs/catalog.md`, not
the skill.** It sits beside § "Closure is not optional" as the same fact read
backwards, and the skill reads it in Step 2 with everything else. Putting it in
the skill would split the closure story across two files and strand the half a
subset adopter never reads. This is the one place the recommendation costs
something — the skill deletes the catalog at Step 5 and cannot re-read it — and
the read-into-the-plan ordering is what pays for it.

**No abstraction is extracted between `/detemplate` and `/spinoff`,** despite
both seeding a project out of this infrastructure. Their triage criteria have
nothing in common: `/spinoff` sorts a hydrated adopter's tree
product-vs-foundation with no inventory to consult, and `/detemplate` decides
catalogued groups against a fork with no product at all. What they genuinely
share is one pointer each at the other's entry point, and both already have it.

**The vet contract collapses from four statements to one home plus three
pointers.** `scripts/vet.sh`'s header, `CLAUDE.md` § "Vetting", `ADOPTING.md` §
"Implement `scripts/vet.sh`" and `docs/catalog.md`'s `rewrite` bullet each state
the exit rule today — and § 2 is the demonstration of what four copies cost,
since the missing clause has to be added to all four or the wrong one gets
followed. `CLAUDE.md` § "Vetting" is the home; it already owns the contract, and
`vet.sh` already says "See CLAUDE.md → Vetting for the contract". `vet.sh`'s
header keeps only what is operational there (what to wire in, what dropping
either non-stack line costs).

**The fork-recognition notice goes in the stub it invalidates.** § 2a's standing
instruction could live in the skill's description alone, in a session-start
hook, or in `CLAUDE.md`. `CLAUDE.md`'s "About this project" stub wins on one
property the others lack: the detemplate run **rewrites that stub**, so the
notice is deleted by the operation it describes rather than needing its own
cleanup step — and a notice that outlived its condition would fire on every
session of a finished project. The hook was the alternative and loses twice: it
runs only when `CLAUDE_CODE_REMOTE` is set, so local sessions miss it, and it
would need explicit removal. The description is kept as well rather than
instead, since the two catch different moments — intent-matching at invocation
versus a standing instruction every session loads.

## Resolved

**The skill is `/detemplate`, and it deletes itself last.** `hydrate` and
`prune` were the alternatives, and each names one half of the job: hydration is
filling the stubs, pruning is deleting the never rows, and the skill does both.
`hydrate` also collides with an existing precise term — `ADOPTING.md` and the
catalog use it for filling a *single* stub, and `check-skill-catalog.sh`
assertion 4 enforces that meaning — so reusing it for the whole-fork operation
makes every existing sentence ambiguous. `prune` reads as repeatable
maintenance, which a once-only self-deleting skill is not. `/spinoff` is the
precedent for the unhyphenated compound. Self-deletion is the operator's
decision; its rationale is in Step 5.7.

**`ADOPTING.md` § "Template fork" becomes a pointer** — a short orienting
paragraph plus "then run `/detemplate <what you're building>`". Its four bullets
go rather than standing alongside the pointer, because the section has no reader
who needs executable steps: a reader **in the fork** has the skill and wants
redirecting; a reader who follows the README's `#template-fork` link **from
GitHub, before forking** wants to know what they are in for, which the
orienting paragraph gives them. The **network reader** — an agent in a foreign
repo reading over HTTPS — only ever uses § "Adopt into an existing repo", which
stays whole and self-contained, since it cannot invoke a skill it does not have.

**Finding 5 shrinks to a prose fix** and the tripwire is dropped — § 2 carries
why. The scope question it raised is moot at four lines of prose.

## Open questions

One, carrying a recommendation the plan above is written with in force — so
silence resolves it and an answer revises the plan.

**1. What does `/spinoff`'s seeded `main` assert about `vet.sh`?** Step 4
currently asserts it exits **non-zero**, calling that "a refusal to certify" on
a `main` that deliberately carries no stack. § 2's clarified rule says a repo
with no stack yet exits `0`, so the two now disagree.

- **(a) Drop the assertion to a positive one — recommended.** Assert `vet.sh`
  exits `0` and that the target has no stack wired, which is the true statement
  about that tree: the loop's own checks pass and there is nothing else to
  check yet. `/spinoff`'s real invariant is that PR #1 is where the stack
  arrives, and that is unaffected.
- (b) Keep the non-zero assertion and exempt `/spinoff`'s seed from the rule.
  Preserves the "loud stop" the step wanted, at the cost of a `main` whose
  `/finalize` cannot pass for a reason the contract calls legitimate.
- (c) Leave `/spinoff` alone in this PR and file the contradiction. Smallest
  diff; leaves two shipped statements in conflict, which is the defect § 2 is
  fixing.
