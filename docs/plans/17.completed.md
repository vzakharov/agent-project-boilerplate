# Issue #17 — `export-github-item.py` never downloads `user-attachments` assets

**Issue:** [#17](https://github.com/vzakharov/agent-project-boilerplate/issues/17) · **Branch:** `claude/user-attachments-s3-auth-z61qfa` (already semantic — no `/branch-rename`)

## Problem

`scripts/export-github-item.py` cannot download any attachment on `github.com/user-attachments/…`, which is where GitHub has served every issue-composer upload since 2024. `/issue` then proceeds without the screenshots and recordings the exporter exists to fetch — silently, because a failed download only prints one line to stderr and the export still reports success.

Two independent causes, both confirmed in this session against #17's sample attachment:

1. **`Authorization` survives the cross-host redirect.** `github.com/user-attachments/assets/<id>` answers `302` to a pre-signed S3 URL. `urllib.request.HTTPRedirectHandler` re-sends every header on the redirected request, so the bearer token follows the hop, and S3 rejects a request carrying both its query signature and that header:

   ```
   400 InvalidArgument — Only one auth mechanism allowed; only the X-Amz-Algorithm
   query parameter, Signature query string parameter or the Authorization header
   should be specified
   ```

   Isolated with curl, which makes the header the decisive variable — `-L` (drops auth cross-host) returns `200` and 59371 bytes; `-L --location-trusted` (keeps it, as urllib does) returns the `400` above.

2. **The remote-session egress proxy refuses the path outright.** In a Claude Code web session, `HTTPS_PROXY` answers `github.com/user-attachments/…` with `403` and `{"message":"This GitHub API path is not available: sessions are bound to their configured repositories. Use repository-scoped endpoints…"}` — before GitHub is reached, so cause 1's redirect never even happens and fixing it alone is not enough here. A direct connection to that same host succeeds, which is the same accommodation `.claude/hooks/session-start.sh` already makes for `gh`, for the same stated reason.

Cause 1 is host-agnostic and reproduces in a local checkout too; cause 2 is remote-session-only. The reported `400` vs. the observed `403` differ only in which cause fires first, which is what made a fixable bug look like a policy wall.

Older `user-images.githubusercontent.com` / `private-user-images.githubusercontent.com` assets are served without the cross-host hop, so a repo whose issues predate `user-attachments` never noticed.

## Fix

Port the patch already verified in [vzakharov/vovazakharov.com#5](https://github.com/vzakharov/vovazakharov.com/pull/5) — this repo is that one's upstream, so the two copies of the script should not diverge. Confined to `scripts/export-github-item.py`:

- **`_host(url)`** — netloc, lowercased.
- **`_DropAuthOnHostChange(urllib.request.HTTPRedirectHandler)`** — delegates to `super().redirect_request`, then `remove_header("Authorization")` when the new URL's host differs from the request's. Addresses cause 1. Keeping the check host-scoped (rather than dropping the header on every redirect) means a same-host redirect that still needs the token keeps it.
- **`_openers()`** — two openers, proxy-honoring first, then one carrying `ProxyHandler({})`. Both install the redirect handler. Order matters: an environment where the proxy is the only egress route keeps working, and the bypass is only ever a fallback. Addresses cause 2.
- **`_request(...)`** — takes an optional `opener`, defaulting to `urllib.request.urlopen` so the API-call paths are untouched.
- **`download_asset(...)`** — tries each opener in turn, breaking on the first success; on total failure prints **both** attempts' errors joined by `"; then "`. The single-attempt message is what disguised cause 1 as cause 2, so reporting both is part of the fix, not polish.

Deliberately unchanged: `api_json` / `api_paginated` keep going through the proxy. They talk to `api.github.com` on repository-scoped paths, which the proxy permits, and `api_paginated` already carries its own accommodation for it. The fallback belongs only on asset downloads, which are the only requests the proxy refuses.

**Error output must stay body-free.** S3's rejection body echoes the offending header value — i.e. the bearer token in full (observed while reproducing this). `download_asset` reports `exc.code`/`exc.reason` and never the response body; the richer two-attempt message must preserve that.

## DRY notes

- **Reused, not re-derived.** `_request` keeps its single definition of the auth/accept/UA header block; the opener is threaded in as a parameter rather than forked into a second request helper. `download_asset`'s existing extension/write/return tail is untouched — only its request attempt becomes a loop.
- **`_host` is a genuine shared need, minimal by design.** Two call sites inside `redirect_request` compare hosts; a one-line helper keeps the comparison (and the `.lower()`) from being written twice inside the same expression.
- **No abstraction over the two openers.** They differ by exactly one handler, so a factory taking a proxy flag would be longer than the literal list and would obscure the load-bearing ordering. The list *is* the policy: read top to bottom, it says "proxy first, direct as fallback."
- **Not extracted: the retry-over-openers loop.** It exists at one call site (`download_asset`) and the API paths must *not* adopt it (see Fix). Generalizing it into `_request` now would push proxy-bypass behavior onto callers that should never have it.
- **Cross-repo duplication is the point.** The patch is a port of the same code in `vovazakharov.com`, a downstream adopter of this boilerplate. Divergence, not duplication, is the failure mode here; landing them identically keeps `/sync-upstream` a no-op on this file.
