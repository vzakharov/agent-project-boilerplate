# #24 — route the stdlib scripts' API calls around a proxy that refuses `api.github.com`

Issue: [#24](https://github.com/vzakharov/agent-project-boilerplate/issues/24) · export: `docs/issue/24/issue.md`

## Problem, confirmed in this session

`export-github-item.py` and `pr-body.py` reach `api.github.com` through a bare
`urllib.request.urlopen`, which honors `HTTPS_PROXY`. This session's egress proxy
refuses every such request, so the first API call kills both scripts. Probed here:

| route | result |
|---|---|
| `python3 scripts/export-github-item.py 24` | `HTTPError 403` — traceback, nothing written |
| proxied `GET /repos/…/issues/24`, no auth | `403 {"message":"GitHub access is not enabled for this session. An org admin must connect the Claude GitHub App for this organization."}` |
| proxied, `Authorization: Bearer $GH_TOKEN` | same `403` |
| direct (`env -u HTTPS_PROXY`), same token | `200` |
| `gh api repos/…/issues/24` | `200` — the `$HOME/.local/bin/gh` shim already runs under `env -u HTTPS_PROXY` |

The refusal is the proxy's own synthetic response, not GitHub's: it is independent
of the URL shape, the token, and the User-Agent. The export of issue #24 on this
branch was only obtainable by running the exporter under `env -u HTTPS_PROXY`.

Two further facts this plan leans on, both verified here rather than assumed:

- **`ProxyHandler` mutates the `Request` it is handed.** `proxy_open` calls
  `req.set_proxy(...)`, which rewrites `req.host` in place. Probed: a `Request`
  for `api.github.com` came back out of a proxied opener with
  `host == '127.0.0.1:37799'`. A single `Request` reused across the ladder
  therefore aims at the proxy on *every* rung, and each later route fails
  identically to the first. `download_asset` escapes this today only because
  `_request` happens to build a fresh `Request` per call inside its loop.
- **The machinery already exists, scoped to attachments.** `export-github-item.py`
  carries `_DropAuthOnHostChange`, `_host` and `_openers()` (the proxy-then-direct
  ladder from #17); `download_asset` walks it and accumulates each rung's failure
  (#22). The API calls in both scripts do neither.

## Approach

Move the ladder into `scripts/lib/github.py` (where #18 put the shared plumbing)
and route all three call sites — the exporter's API reads, the exporter's
attachment downloads, and `pr-body.py`'s REST calls — through one helper that owns
both the walk and the failure accumulation.

### 1. `scripts/lib/github.py` — own the ladder and the walk

Add, alongside the existing `die` / `gh_token` / `detect_origin_repo`:

- `_DropAuthOnHostChange` and `_host`, moved verbatim from `export-github-item.py`
  (docstring included — it records why S3 rejects a redirected request that still
  carries `Authorization`).
- `_openers()`, moved verbatim: proxy-honoring opener first, then one built with
  `ProxyHandler({})`. Order is load-bearing — an environment where the proxy is
  the only route out keeps working, so this whole change is additive.
- `RouteFailure(NamedTuple)` — one rung's refusal, captured eagerly as
  `status: str` (e.g. `"403 Forbidden"`, or a `URLError`'s reason) and `body: str`
  (`""` when there was none). Eager capture matters: an `HTTPError`'s body is
  readable once, off a file object whose lifetime is not ours to hold open across
  the rest of the ladder.
- `AllRoutesFailed(Exception)` — carries `failures: list[RouteFailure]` in ladder
  order. Its `str()` joins the status lines with `"; then "`, matching the string
  `download_asset` produces today; bodies stay on the attribute so a call site
  opts into them rather than leaking them by default.
- `fetch(build_request) -> tuple[bytes, dict[str, str]]` — walk the ladder,
  calling `build_request()` **once per rung**, return the first success as
  `(body, lowercased headers)`, and raise `AllRoutesFailed` when every rung
  refused. Taking a *factory* rather than a `Request` is what structurally
  enforces the fresh-request rule above; a comment on the parameter says so, so
  nobody "simplifies" it back into a plain argument.

### 2. `scripts/export-github-item.py` — delete the local copies, route the reads

- Drop `_DropAuthOnHostChange`, `_host` and `_openers()`; import `fetch`,
  `AllRoutesFailed` and `RouteFailure` from `lib.github`.
- `_request(url, token, accept)` loses its `opener` parameter and returns
  `fetch(lambda: urllib.request.Request(url, headers={...}))`. Both `api_json`
  and the attachment path inherit the ladder from this one change.
- `download_asset` stops looping openers itself: one `_request` call, catching
  `AllRoutesFailed` and re-raising `AttachmentDownloadError` built from the
  failures' **statuses only**. `AttachmentDownloadError`'s docstring already
  explains why (S3's rejection body echoes the offending header — the bearer
  token in full); keep it, and keep the body-free construction it describes.
- `main` grows an `except AllRoutesFailed` around the API work that `die`s with
  every rung's status **and** body, in order. Unlike S3, `api.github.com` and the
  proxy answer with their own JSON and never echo request headers, so the bodies
  are safe here — and they are the whole diagnostic: `403 "GitHub access is not
  enabled for this session"` then `404 Not Found` reads very differently from
  either half alone.

### 3. `scripts/pr-body.py` — route the REST calls

- `api()` builds its `Request` inside a factory and calls `fetch`, replacing the
  bare `urlopen`. The `HTTPError` branch becomes `except AllRoutesFailed`, dying
  with `f"{method} {path} failed:"` followed by one line per rung
  (`status` + `body`), preserving today's shape for the single-rung case.
- Retrying the `PATCH` on the direct route is safe: a rung that refused never
  reached GitHub, and a body PATCH that *did* land is idempotent under a repeat.

### 4. `.claude/skills/override-gh/SKILL.md` — one sentence

That skill is where the repo records that `gh` is shimmed around the proxy. Add a
sentence saying the stdlib Python scripts now carry their own proxy-then-direct
ladder, so they need no shim and no `env -u` prefix either. Nothing else in the
docs changes.

## Cost accepted

On a genuine error (a real `404`), every request is now made twice before the
script reports. That is already the attachment path's behavior and the price of
not guessing which rung is the closed one; the doubled call only happens on the
failure path, and the accumulated pair is what makes the report legible.

## DRY notes

- **Genuinely shared, and now shared once:** the opener ladder, the redirect
  handler, and the walk-and-accumulate loop. All three call sites (exporter API
  reads, exporter attachment downloads, `pr-body.py` REST) want the identical
  behavior, and the loop is the part most likely to drift if copied — #22's
  accumulate discipline exists in exactly one of the three places today, which is
  the drift already having happened once. `lib/github.py` is the established home
  (#18) and both scripts already import from it.
- **Reused rather than re-derived:** `_DropAuthOnHostChange`, `_host` and
  `_openers()` move verbatim — no reimplementation, no behavior change to the
  attachment path. `RouteFailure`'s `"; then "` join reproduces the exact string
  `download_asset` raises today.
- **Deliberately not extracted:** the *formatting* of a failure. The attachment
  path must omit bodies (token echo) and the API paths must include them (the
  bodies are the diagnostic), so `AllRoutesFailed` carries structured failures and
  each call site renders them. Forcing one formatter would mean a boolean
  parameter selecting between two unrelated safety rules — a flag that reads as an
  option but is really a security constraint.
- **Deliberately not extracted:** `api_json` (exporter) and `api()` (pr-body) stay
  separate. They differ in method, payload, `USER_AGENT` (which is how the two are
  told apart server-side — `lib/github.py`'s docstring already calls this out) and
  error disposition; the part they share is precisely `fetch`, which they now both
  call.

## Open questions

Both are answered in the plan above by their recommended option, so the plan is
implementable as written if neither is answered.

**1. Where does the walk-and-accumulate loop live?**

- **(a) — recommended, and what this plan assumes.** In `lib.github.fetch`, with
  `_openers()` module-private. One copy of the loop, three callers.
- (b) Export `openers()` from `lib.github` as the issue's text literally says, and
  keep the `for opener in openers(): try/except` loop written out at each of the
  three call sites. Closer to the issue, but it is the copy that already drifted
  once.

**2. Do API failure messages include each rung's response body?**

- **(a) — recommended, and what this plan assumes.** Yes for the API paths, no for
  attachments. The proxy's 403 body is the sentence that tells you the proxy —
  not GitHub — refused, and `api.github.com` never echoes request headers.
- (b) Statuses only everywhere, matching `download_asset`'s existing caution. Safer
  by uniformity, but `403 Forbidden; then 404 Not Found` on its own does not tell
  you which rung is the closed one.
