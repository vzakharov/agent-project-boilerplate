# Issue #11 — state `/plan` and `/implement`'s durable rationale in the skills themselves

Issue: https://github.com/vzakharov/agent-project-boilerplate/issues/11 (export at `docs/issue/11/`)

## Problem

The only place this repo argues that `/plan` and `/implement` are worth having is
`README.md` and the `/plan` closure note in `docs/catalog.md` — both **`never`**
rows in the catalog, i.e. never copied into an adopting repo. What *does* travel
is `/plan`'s own framing, and that framing is bug-first on both of its surfaces:
the frontmatter `description` ("for web/remote sessions where those UIs are
buggy") and the body's opening "Why this skill exists" section, which is entirely
about the re-emitted prompts.

An adopter reading only `.claude/skills/` therefore concludes two wrong things:
that `/plan` is dead weight in a local-only repo, and that it becomes dead weight
the day [anthropics/claude-code#72704](https://github.com/anthropics/claude-code/issues/72704)
is fixed. `/implement` has the mirror gap: it states that reaching it *is* the
go-ahead, but never says why the plan-file flip is worth doing on the record —
that rationale is inferable only from `/plan`.

Scope is deliberately narrow: two skill files, prose only. No behavior, no
scripts, no new files.

## Not split-worthy

Two files, one cohesive argument, prose only. Splitting would invent seams.

## Step 1 — Rewrite `/plan`'s frontmatter `description`

It is a **separate surface** from the body (the operator scans it in the skills
list; an invocation matches against it), so it needs the fix independently — the
same two-surface problem `check-skill-catalog.sh` assertion 4 exists for.

Requirements it must keep satisfying:

- Retains the tokens that make invocation match: *plan mode*, *AskUserQuestion*,
  *docs/plans/*, *remote/web session*.
- Leads with what the skill **is**, not with the bug.
- Mentions web/remote as where it is **mandatory**, not as the reason it exists.

Proposed replacement (single-line `description:`, refined for length at write
time):

> Plan on disk instead of in the plan-mode UI: write the plan to a reviewable,
> git-tracked file under `docs/plans/` whose name doubles as the approval gate,
> and ask clarifying questions as numbered prose instead of `AskUserQuestion`.
> Use whenever you would otherwise enter plan mode or call `AskUserQuestion` —
> mandatory in web/remote sessions, where both of those UIs also lose answers.

## Step 2 — Rewrite `/plan`'s "Why this skill exists"

Restructure the section so the durable value is the section and the bug is a
closing **Origin** note. Content to state, one bullet each:

- **Reviewable on another machine, on the operator's schedule** — the plan rides
  the branch, so it is pulled and read in the same tools as code, hours later.
- **Room for sections plan mode has nowhere to put** — notably the mandatory
  `## DRY notes`, which forces the reuse-vs-duplication call to be argued before
  any code exists rather than discovered in review.
- **The filename is the approval gate** — `*.draft.do-not-implement.md` says in
  every `ls`, tool-call path and `git status` that nothing is cleared, and the
  `git mv` that clears it is a commit, so *when* approval arrived and *in whose
  words* outlives the session.
- **Approval carries into the next session** — the turn ends with a copyable
  `/implement <branch>` line, so implementation starts with the decision
  recorded instead of re-litigated.
- **Questions as numbered prose stay in the transcript** — tersely answerable
  ("1b, 2a"), and re-readable after a context wipe.

Then one sentence stating outright that none of this depends on plan mode being
broken, so the skill does not retire when the bug is fixed.

Then an **Origin** paragraph carrying the existing bug description (idle session
→ backend re-wakes → stacked plan/question prompts → answers to superseded
prompts silently lost, count scaling with idle duration; operators run many
concurrent web sessions so prompts routinely idle) — reframed as *why web/remote
is the case where the file-based path is mandatory rather than merely better*,
pointing at CLAUDE.md § "Plan mode & questions in web sessions". The tracking
link survives here, labelled as history/status rather than as the rationale.

Length target: no longer than the section it replaces plus a few lines. This is a
skill file read on every load, not an essay.

## Step 3 — Give `/implement` the matching statement

Extend the opening paragraph (or add one short paragraph after it) with two
things it currently leaves to inference:

- **What it assumes**: approval already happened; invoking `/implement` — or
  reaching it via `/plan`'s gate or `/from-branch … implement` — *is* the token.
  (Already said; keep, don't duplicate.)
- **Why the flip is on-record**: Step 1's `git mv` out of
  `*.draft.do-not-implement.md`, plus the operator's literal go-ahead quoted in
  that commit message, is the branch's own record of when this plan was cleared
  and in what words. Nothing else in the history distinguishes an approved plan
  from one somebody just started implementing — which is why it lands before the
  first source edit rather than as cleanup afterwards.

Keep this to a couple of sentences. `/implement` Step 1 already owns the
mechanics; this states the *why* once, next to the assumption it justifies.

## DRY notes

- **Genuinely shared, deliberately not extracted.** The argument for file-based
  planning now appears in three places, and that is the issue's explicit intent
  (criterion 4 asks for *one copy per audience*, not one copy total). There is no
  include mechanism for skill frontmatter or Markdown prose here, and the three
  audiences need different framings — evaluator, adopter-deciding-a-subset, agent
  holding only the skills tree. Forcing a single shared paragraph would either
  land in a file adopters never receive (defeating the point) or flatten three
  registers into one that serves none. The mitigation is editorial, not
  structural: Step 4's table fixes what each site is responsible for saying.
- **Reused, not restated.** The mechanics of the plan-file lifecycle stay in
  `/plan` § "Plan file lifecycle" and the flip stays in `/implement` § "Step 1";
  the new prose *names* them and states why they matter, and does not re-describe
  how they work. Same for CLAUDE.md § "Plan mode & questions in web sessions",
  which keeps owning when the skill is mandatory — the Origin note points at it.
- **Duplication actively removed:** none. Nothing in this diff is a second copy
  of a mechanism; the bug description moves within `/plan` rather than being
  copied.
- **No new files, helpers or scripts**, so no shared-abstraction call beyond the
  above.
