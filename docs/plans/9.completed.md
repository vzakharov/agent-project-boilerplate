# Issue #9 — Port PR support into the GitHub export script

Extend `scripts/export-github-issue.py` to export pull requests as well as
issues, rename it `scripts/export-github-item.py`, and update every reference.
Stdlib-only Python 3.9+ throughout — no new toolchain reaches an adopter.

**Not split-worthy.** One script, one rename, and a handful of one-line
reference updates. Single subsystem, single PR.

## What the donor actually has (findings, read from `Playgramai/playgramapp@scripts/export-github-item.ts`)

The issue's step 1 predicted the donor's PR support was "review threads, review
comments and diff hunks … where the real work is". **It is not.** The donor's
TypeScript version is a near-line-for-line twin of our Python script, and its
entire PR delta is:

| Donor change | Lines |
| --- | --- |
| URL regex accepts `/pull/N` as well as `/issues/N` | 1 |
| PR detected from the issues payload's `pull_request` field | 1 |
| Output routed to `docs/pr/<n>/pr.md`, header says `PR #n` | ~5 |
| Timeline noun parameterised (`this issue` / `this pull request`) | ~30 (switch churn) |
| Six PR-only timeline events: `merged`, `reviewed`, `ready_for_review`, `convert_to_draft`, `review_requested`, `review_request_removed` | ~25 |
| Attachment regex also matches `user-attachments/files/…` (uploaded documents, not just inline images) | 1 |

It never calls `/pulls/<n>/reviews` or `/pulls/<n>/comments`. A PR exported by
the donor carries a timeline line saying *"@x reviewed (CHANGES_REQUESTED):
<url>"* and **none of the review's text, none of the inline comments, and none
of the diff hunks they hang off**. The one substantive improvement over ours is
the `user-attachments/files/` regex arm, which is an issue-side bug fix we're
missing today regardless of PRs.

So a literal port lands ~60 lines and produces PR exports that are worse than
`gh pr view` for the thing PRs are actually read for. This plan does the port
**and** fills that gap, because the issue's own framing says review threads are
the point.

## Approach

### 1. Teach the script to export PRs

In `scripts/export-github-issue.py`:

- **Args.** Widen the URL regex to `/(?:issues|pull)/(\d+)`. A bare number stays
  a bare number — the type is discovered from the API, not from the argument, so
  `9` works whether #9 is an issue or a PR.
- **Detection.** Keep fetching `repos/<repo>/issues/<n>` (the issues endpoint
  serves PRs too, and is the only one that returns the conversation comments and
  timeline). `issue.get("pull_request") is not None` ⇒ PR.
- **Routing.** PR ⇒ `docs/pr/<n>/pr.md`; issue ⇒ `docs/issue/<n>/issue.md`
  unchanged. Attachments stay under `<out-dir>/attachments/`.
- **Header.** `# PR #n: <title>` vs `# Issue #n: <title>`. For a PR, add three
  lines the issues payload can't supply, from `repos/<repo>/pulls/<n>`:
  `- **Base ← Head:** main ← claude/foo`, `- **Draft:** yes/no`,
  `- **Merged:** <merged_at or _not merged_>`.
- **Timeline.** Parameterise the noun and add the donor's six PR events. Our
  `_STATIC_TIMELINE_SUFFIXES` table is the natural home for `ready_for_review` /
  `convert_to_draft` / `merged`; `reviewed` and the two `review_request*` events
  need the same `_timeline_suffix` branch treatment the donor's switch gives
  them. The noun threads through as a parameter rather than being baked into the
  table's strings.
- **Attachments.** Add the `user-attachments/files/` arm to
  `ATTACHMENT_URL_RE`. Applies to issues too — a straight fix.

### 2. Add the review threads the donor omits (the part with no issue equivalent)

For a PR only, fetch two more paginated endpoints and emit a
`## Review threads` section between `## Comments` and `## Timeline`:

- `repos/<repo>/pulls/<n>/reviews` — review bodies with `state`
  (`APPROVED` / `CHANGES_REQUESTED` / `COMMENTED`), author, `submitted_at`.
- `repos/<repo>/pulls/<n>/comments` — inline review comments, each carrying
  `path`, `line`, `diff_hunk`, `body`, `pull_request_review_id`, and
  `in_reply_to_id`.

Rendering: group comments into threads by walking `in_reply_to_id` to its root,
order threads by their root's `created_at`, and render each as a
`### <path>:<line>` heading, the root's `diff_hunk` in a ```` ```diff ```` fence
(once per thread — replies share it), then each comment as author + timestamp +
body. Reviews whose body is non-empty print above the threads as
`### Review by @x — CHANGES_REQUESTED`; a review with an empty body and no
comments is already covered by the timeline line and is skipped.

Comment and review bodies go through the same attachment collection/rewrite pass
as the issue body, so screenshots pasted into a review are downloaded too.

Skipped for issues (the endpoints 404), so the issue path costs no extra
requests.

### 3. Fix the `docs/pr/<n>/` collision

`scripts/pr-body.py push` currently does `shutil.rmtree(docs/pr/<n>/)`, and
`/qa-checklist` tells the agent to `rm -rf docs/pr/<n>`. With an export living
at `docs/pr/<n>/pr.md`, a QA-checklist run would silently delete it. Make both
cleanups surgical:

- `pr-body.py`: unlink `body.md`, then `rmdir` the parent, ignoring
  `OSError` when it isn't empty. Drop the now-unused `shutil` import.
- `/qa-checklist` line 74: `rm -rf docs/pr/<n>` → `rm -f docs/pr/<n>/body.md`.

This is the reason the two trees can share a root at all; without it the sharing
is a live footgun.

### 5. Verify

- `python3 scripts/export-github-item.py 9` → `docs/issue/9/issue.md`, byte-identical to today's output except for the header (regression check that the issue path didn't move).
- `python3 scripts/export-github-item.py 7` → `docs/pr/7/pr.md` with review threads (PR #7 has review activity).
- `python3 scripts/export-github-item.py https://github.com/vzakharov/agent-project-boilerplate/pull/7` → same output via URL form.

## DRY notes

- **Genuinely shared, and already factored:** every helper the PR path needs —
  `api_paginated`, `_request`, `collect_attachment_urls`, `download_asset`,
  `rewrite_attachment_refs`, `slug_from_url`, `extension_for_bytes` — is already
  generic over the payload. The PR path calls them unchanged; nothing is copied.
- **Parameterised, not duplicated:** the timeline renderer takes the noun as an
  argument. The alternative (an issue table and a PR table) would duplicate all
  ten shared events to vary one word.
- **Deliberately *not* extracted:** `pr-body.py` and `export-github-item.py`
  both carry `gh_token()`, `detect_origin_repo()` and a small `api()`. That
  duplication is pre-existing and stays. Extracting a `scripts/lib/gh.py` would
  make each script non-copyable on its own, and this repo's whole distribution
  model is adopters copying individual files out of `scripts/` (see
  `docs/catalog.md`'s per-file rows and `scripts/lib/`'s absence from any
  catalog row). Self-containment beats DRY here, and the issue's constraint —
  no new prerequisite for an adopter — points the same way.
- **New code that is genuinely new:** the review-thread grouping and diff-hunk
  rendering (§2) has no existing counterpart in either repo. It lives in two
  small functions (`review_threads`, `review_section`) beside the existing
  `timeline_section`, matching its shape.

## Open questions

Each has a recommendation, and the plan above is written with the recommendation
already in force — so silence is a valid answer.

1. **Do we add the review threads (§2), or stop at donor parity?**
   **(a) Add them — recommended.** The issue names review threads/comments/diff
   hunks as the substance of PR support; parity alone delivers a PR export that
   omits exactly that. Cost is ~100 lines and two extra API calls on the PR path.
   **(b) Donor parity only.** Smaller diff, keeps us byte-aligned with upstream,
   but ships a PR exporter nobody would use over `gh pr view`.

2. **Should `/issue` accept a PR argument?** (Issue's step 4.)
   **(a) No — recommended.** `/issue` is a workflow skill: export → split →
   implement → PR. None of that means anything for a PR. `/from-branch` is
   already the PR entry point, and it gets a pointer to the new script instead.
   **(b) Yes**, `/issue #N` detects a PR and degrades to "export and report" —
   two skills' worth of behaviour behind one name.

3. **Output path for PR exports.**
   **(a) `docs/pr/<n>/pr.md` — recommended.** Donor parity, and `/finalize`
   already sweeps `docs/pr/` wholesale so AC #3 comes for free. Requires the §3
   collision fix, which is worth doing on its own merits.
   **(b) A third root** (`docs/pr-export/<n>/`). Avoids the collision without
   touching `pr-body.py`, but diverges from the donor and adds a tree that
   `/finalize`, the catalog, and `check-skill-catalog.sh` all have to learn.
