### Step 3 — derive the watermark, which git cannot give you

**Finding 3.** A template fork's single commit has no ancestry in the source, so
`git rev-parse HEAD` in a clone — `ADOPTING.md`'s recipe — is a clone a template
forker never made. Derive it instead by matching the source's commit list
against the fork's creation time:

```bash
gh api repos/<owner>/<fork> --jq .created_at
gh api repos/vzakharov/agent-project-boilerplate/commits --paginate \
  --jq '.[] | [.sha, .commit.committer.date] | @tsv'
```

The newest source commit at or before the fork's `created_at` is the mark.

**Finding 4.** `lineage` is written in the same breath:
`[{ "repo": "vzakharov/agent-project-boilerplate", "atSha": <the same sha> }]`.
The two fields start equal and diverge on the first sync — per
`@.claude/skills/sync-agent-infra/SKILL.md` § "The watermark", `lastSyncedSha`
advances and `lineage[0].atSha` never moves — and that first sync is what
overwrites the only other trace of the birth point. A watermark written without
it loses the birth point permanently.

## 2 — `scripts/vet.sh`: the third state

**Finding 5.** Two states leave a fork with no stack yet — the normal state of a
fork taken to start a project — with no honest option. `exit 1` fails step 1 of
`/finalize` on every prose-only PR, which trains the loop to route around the
vet run; `exit 0` is a false green the day a stack lands.

The missing state: **exit 0, and trip the moment a stack manifest appears with
nothing wired to it.** The tripwire ships in the boilerplate's own `vet.sh`,
inert here because there is no manifest, and self-arming in the fork the day one
is added — so nobody has to remember to add it later. It names **two** wiring
sites, not one:

- `scripts/vet.sh` itself, and
- `.claude/hooks/session-start.sh`'s dependency install, which **nothing at all
  catches** today.

Shape: glob for the manifests (`package.json`, `pyproject.toml`, `Cargo.toml`,
`go.mod`, `Gemfile`, `pom.xml`, `build.gradle*`, `composer.json`, `*.csproj`,
`mix.exs`) — a list that goes stale by construction, so the failure message says
so and tells the reader to add theirs rather than implying the list is complete.
Present and neither site wired → fail, naming both. Absent → the current exit-0
message, amended to say what will trip it.

The "wired" test is the honest-signal question and the one place a cheap answer
would undo the point: it must be a positive mark rather than "the file changed".
Recommended: a sentinel line each site must carry (`# vet: stack wired` /
`# session-start: deps wired`), so the tripwire reads a claim someone made
rather than inferring one.

## DRY notes

**The template-fork procedure gets one home, and it is the skill.** Today it is
`ADOPTING.md` § "Template fork"; leaving it there and adding a skill that reads
it creates exactly the two-homes drift `CLAUDE.md` § "Writing things down"
names. The section becomes a pointer. Which of the two is the home is settled by
audience: `ADOPTING.md` is read **over the network, from a clone, by a session
that has none of these skills**, and its subset path must stay whole for that
reader; the template-fork path is read **in-tree, by a session that has every
skill**, so a skill is its natural home and a pointer covers the reader who
arrives at `ADOPTING.md` by mistake.

**The shared tail stays in `ADOPTING.md`; the skill restates only what actually
differs.** Three of its five steps have a materially different fork form — the
watermark SHA has no clone to read (finding 3), `vet.sh` takes the third state
rather than the adopter's `exit 1`, and the catalog-delete ordering has no
subset analogue at all. Those are new content, not copies. The two that are
identical — hydrate-or-delete G6, and `CLAUDE.md`'s stub — get one line each
pointing at the catalog rows the skill has already read. Forcing the differing
three into a shared statement would produce a paragraph hedged for two readers
and precise for neither.

**Reverse closure is inventory knowledge, so its home is `docs/catalog.md`, not
the skill.** It sits beside § "Closure is not optional" as the same fact read
backwards, and the skill reads it in Step 2 with everything else. Putting it in
the skill would split the closure story across two files and strand the half a
subset adopter never reads. This is the one place the recommendation costs
something — the skill deletes the catalog at Step 5 and cannot re-read it — and
the read-into-the-plan ordering is what pays for it.

**No abstraction is extracted between `/de-template` and `/spinoff`,** despite
both seeding a project out of this infrastructure. Their triage criteria have
nothing in common: `/spinoff` sorts a hydrated adopter's tree
product-vs-foundation with no inventory to consult, and `/de-template` decides
catalogued groups against a fork with no product at all. What they genuinely
share is one pointer each at the other's entry point, and both already have it.

**The vet contract collapses from four statements to one home plus three
pointers.** `scripts/vet.sh`'s header, `CLAUDE.md` § "Vetting", `ADOPTING.md` §
"Implement `scripts/vet.sh`" and `docs/catalog.md`'s `rewrite` bullet each state
the exit rule today; a third state would make that four places to keep in step.
`CLAUDE.md` § "Vetting" is the home — it already owns the contract, and `vet.sh`
already says "See CLAUDE.md → Vetting for the contract". `vet.sh`'s header keeps
only what is operational there (what to wire in, what dropping either non-stack
line costs).

## Open questions

Each carries a recommendation, and the plan above is written with all four
recommendations in force — so silence resolves them and an answer revises the
plan.

**1. The name.** The issue leaves it open.

- **(a) `/de-template` — recommended.** Says exactly what the operation is,
  reads as one-time, and collides with nothing.
- (b) `/adopt` — overreaches: `ADOPTING.md` has two modes and this skill serves
  only one, the other being unreachable from a session in the target repo.
- (c) `/start-project` — matches the argument shape (`/<name> <what we're
  building>`) but describes the outcome rather than the operation, and reads as
  a scaffolder that writes product code.

**2. Does a hydrated fork delete the skill, or keep it as the re-run lane?**

- **(a) Delete itself, last — recommended.** Its job is done once, like
  `ADOPTING.md`, and its inputs (the catalog, `ADOPTING.md`) are gone by the
  time it finishes, so what survives is a skill that cannot re-run its own
  procedure. The re-run need is real but it is a *different* job — wiring a
  stack that finally landed — and finding 5's tripwire already carries it, by
  naming the two wiring sites at the moment the stack appears. That is a better
  lever than a skill nobody remembers to re-invoke.
- (b) Keep it. Costs a permanent row describing an operation already performed,
  and the kept copy would need its deleted inputs inlined to be runnable.

**3. Does finding 5 (the third vet state) land in this PR or its own?**

- **(a) This PR — recommended.** The skill has nothing honest to write into a
  stackless fork's `vet.sh` without it, so splitting leaves the skill's Step 5.6
  blocked on another PR.
- (b) Its own issue. Cleaner diff, at the cost of shipping a skill with a hole
  in it.

**4. Does `ADOPTING.md` § "Template fork" become a pointer, or stay the home?**
The § "DRY notes" argument above is the case for **(a) pointer — recommended**;
**(b)** keeps the prose where a network reader finds it, and accepts two homes.
