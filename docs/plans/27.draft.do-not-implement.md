# #27 — Lint suppressions: state where an approved suppression goes

Source: [`docs/issue/27/issue.md`](../issue/27/issue.md) · issue
[#27](https://github.com/vzakharov/agent-project-boilerplate/issues/27)

## The change in one line

Add one bullet to `CLAUDE.md` § "Key principles", immediately after the
existing `Never add lint-suppression comments…` bullet, saying **where** an
approved suppression goes.

## Scope survey

`grep` over the repo for `suppress|eslint-disable|noqa|type: ignore|nolint`
finds exactly one governing statement: `CLAUDE.md:42`. Nothing in
`.claude/skills/`, `.claude/rules/` (ships empty by design), or `scripts/`
encodes suppression policy, so there is one file to change and no
cross-references to keep in sync. `docs/catalog.md`'s `CLAUDE.md` row
summarises the file by section, not by principle, so it does not move.

## Does this belong in the boilerplate?

Yes. The issue's own comment doubts it — "I'm not sure if this was ever a
problem here or if it's something the consumer repo introduced" — but a
boilerplate's `CLAUDE.md` is not a log of this repo's incidents; it is the
convention set a new project starts from, and every other bullet in "Key
principles" is there without this repo having been bitten by it. The rule is
as stack-agnostic as the bullet it extends, and the repo currently has no
lintable source at all, so "it never happened here" is a statement about the
repo being a seed, not about the rule's value.

## Rationale to encode

Lead with the framing from the issue comment, which is the stronger of the
two and generalises past linters to any central config:

> we want to suppress stuff at the shallowest place where it makes sense.
> eslint should ideally NOT know anything about what kind of code it lints —
> a "we do need to dangerously render html in an article body" is a concern
> it should never have to deal with, otherwise it makes it less portable.

That is a dependency-direction argument: the config is a lower layer and must
not acquire knowledge of the domain above it. Keep the issue body's point as
the secondary clause — a central entry is invisible from the code it exempts,
so it outlives that code silently and nothing points at the stale ones.

## The text to add

A new sibling bullet, placed directly after the existing suppression bullet so
"whether" and "where" read in order:

```markdown
- **An approved suppression goes at the point of use, not in the linter's
  config.** Once the user has agreed to one, put it on or immediately above the
  offending code with the rationale in the same comment, so whoever edits that
  line reads why. Suppress at the shallowest layer that knows enough to justify
  it: the linter's config should not have to know what kind of code it lints —
  "this article body really does render trusted HTML" is a domain concern, and
  a config that carries domain concerns stops being portable. A central entry
  (`eslint.config.*`, `pyproject.toml`'s `per-file-ignores`, `.golangci.yml`) is
  also invisible from the code it exempts, so it outlives that code silently.
  Reserve central-config exemptions for a suppression that genuinely spans
  files — a whole directory, a migration backlog — and have it name them
  explicitly.
  - A file-level suppression at the top of the file is the point-of-use form
    when every occurrence in the file shares one reason (a CLI whose stdout is
    its interface, a module that must augment a library type). The test-file
    exception above is one instance of this.
  - A permanent exemption states the invariant that makes it correct; a
    temporary one names the issue tracking its removal.
```

Two sub-bullets, where every other entry in "Key principles" is flat. The
deviation is deliberate: the parent is already at the section's upper length
bound, and both corollaries are conditionals ("when X, the form is Y") that
read as run-ons when inlined. Easily reversed if you'd rather keep the section
uniform.

The existing bullet is left untouched.

## DRY notes

Nothing is extracted or shared — the change is one Markdown bullet — but there
are two live duplication questions:

- **Against the existing test-file exception.** `CLAUDE.md:42` already permits
  file-level suppression in test files for mocking mechanics. The new
  corollary about file-level suppression could restate it. It does not: the
  existing clause answers *when a suppression in tests is allowed at all*, the
  corollary answers *why the file-level form counts as point-of-use*. The
  corollary names the test exception as an instance rather than repeating its
  content, which is the link without the copy.
- **Against the consumer repo's `.claude/rules/eslint.md`.** The precedent repo
  holds ESLint-specific policy (which rules, which exemptions). This bullet
  deliberately carries only the stack-agnostic half — placement — so the two do
  not overlap; the ESLint-shaped material stays downstream, where a rule file
  scoped to lint config is the right home for it. Pulling that material up here
  would be net-negative: this repo has no ESLint and no lintable source, so it
  would be unverifiable convention that drifts from whatever the consumer
  actually ships.
- **No new file.** A `.claude/rules/` entry was considered and rejected: rules
  are path-scoped and load only when a matching file is touched, whereas this
  applies wherever a linter runs, which is everywhere. It belongs in the
  always-loaded file.
