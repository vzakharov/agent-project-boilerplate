## Body

`scripts/check-squash-message.sh` enforces `TITLE_MAX_CHARS=80` and `BODY_MAX_WIDTH=72` with `${#line}`:

```sh
[ "${#line}" -le "$title_widest" ] || title_widest=${#line}     # :196
if [ "${#line}" -gt "$TITLE_MAX_CHARS" ]; then                  # :197
  title_over="${title_over}${NL}    ${#line} chars: ${line}"    # :198
…
[ "${#line}" -le "$body_widest" ] || body_widest=${#line}       # :225
if [ "${#line}" -gt "$BODY_MAX_WIDTH" ]; then                   # :226
  body_over="${body_over}${NL}    line ${body_lines} (${#line} chars): ${line}"  # :228
```

`${#var}` counts **bytes** in `dash` — which is `/bin/sh` on Debian and Ubuntu, and the script is `#!/bin/sh` on purpose — and also in `bash` outside a UTF-8 locale. The caps are terminal columns (`git log` indents a body by 4 in an 80-column terminal), so what they should count is characters. The two agree only while the message is ASCII, which is why this has stayed invisible.

For any script beyond Latin-1 the effective cap is roughly halved: UTF-8 spends two bytes per character on Cyrillic, Greek, Hebrew and Arabic, three on CJK. A body wrapped correctly at 72 columns is rejected, and the only way to pass is to wrap at ~36 columns, which is not the format the skill asks for. The failure output compounds it by reporting the byte count under the label `chars`, so the operator is told a 62-character line is 116 characters long.

### Repro

```sh
$ printf 'Proposed squash title/body:\n\n```\nchore: fine\n```\n\n```\n%s\n```\n' \
    "$(python3 -c 'print("я"*40 + " " + "ю"*31)')" > /tmp/p.md   # 72 characters
$ sh scripts/check-squash-message.sh /tmp/p.md
check-squash-message: FAIL — /tmp/p.md (given)
  1 body line(s) over 72 chars:
    line 1 (143 chars): яяяя…
```

### Why it matters

`scripts/vet.sh` calls this check, and `/finalize` gates on the vet run. So an adopting project whose convention puts human-facing text — commit messages included — in a non-Latin script cannot land anything: the squash proposal fails the width check no matter how it is wrapped, and the only workarounds are wrapping to half the intended column or dropping the check.

### Suggested fix

Deleting UTF-8 continuation bytes (`10xxxxxx`, i.e. `\200-\277`) leaves exactly one byte per character, so `tr` gets there without adding an interpreter to the script's dependency floor — a constraint the file's own header states:

```sh
# The caps are terminal columns, so they count characters — but `${#line}`
# counts bytes under `dash`, and under `bash` outside a UTF-8 locale, which
# agrees only while the message is ASCII. Deleting UTF-8 continuation bytes
# leaves one byte per character.
char_len() {
  s=$(printf '%s' "$1" | LC_ALL=C tr -d '\200-\277')
  printf '%s' "${#s}"
}
```

Then compute `len=$(char_len "$line")` once per line and use `$len` at the five sites above. `is_blank` and `is_wrappable` need no change — they test for the presence of whitespace, not length.

`wc -m` is the other obvious route and is worse here: it reports bytes under `LC_ALL=C` and needs a UTF-8 locale to be present and named correctly, which differs between glibc (`C.UTF-8`) and macOS (`en_US.UTF-8`).

Worth covering all four boundary cases when this is fixed, since three of them pass today for the wrong reason: 72 characters passes and 73 fails, in ASCII **and** in a two-byte script. A green run on the fixed script proves nothing on its own — the byte version also goes green on short input.

### Scope

This is the only site. Every other `${#…}` under `scripts/` is an array length (`${#sources[@]}`, `${#stubs[@]}` in `check-skill-catalog.sh`, `${#REPO_FLAG[@]}` in `ci-watch-tick.sh`), where bytes-vs-characters doesn't arise — so the fix is one file, not a sweep.
