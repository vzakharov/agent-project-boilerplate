## Body

`/sync-upstream` is written as one link in an adoption chain — "'Upstream' is relative to the repo you are standing in", with "the application repo its infrastructure was extracted from" named as this repo's own source. `.claude/skills/sync-upstream/upstream.json` acts on that, naming `Playgramai/playgramapp` and adopting effectively everything.

That arrangement no longer describes anything. This repo is the origin of the agent infrastructure its adopters run; `Playgramai/playgramapp` is now an adopter of it like any other (its skill is `/sync-agent-infra`, watermarked at `.claude/skills/sync-agent-infra/upstream.json`). With adopters on both sides of a `upstream.json` pointing back at one of them, the two repos each read the other as their source — a loop with no root.

This repo has no upstream. The ask is to say so, in the four places that currently imply otherwise.

## 1 — `/sync-upstream` becomes a G6 stub

There is no repo to sync from, so the skill has no procedure to run here — but the *shape* of the job is exactly what an adopter needs, which is what G6 is for: "only the durable part: the shape of the job, and the concerns any implementation has to answer."

Keep: the watermark's structure and its `adopted`/`declined` contract, the two invariants (never sync the watermark; judge the diff, not the commit message's "we"), the verdict table, the "apply by intent, not by patch" rule, and the Step 2 clone recipe (the `clone -c` credential-helper trap in particular — it is the kind of thing an adopter would otherwise rediscover the hard way).

Drop: `lastSyncedSha` as a live value, and anything that reads as this repo having a source of its own.

**Both stub markers must be set together.** `scripts/check-skill-catalog.sh` assertion 4 requires a `> ⚠️ **STUB.**` banner in the body *and* the frontmatter `description:` to say so — it fails either way round ("carries a STUB banner but its description does not say so", "described as a STUB but has no banner").

## 2 — Rename it to `sync-agent-infra`

The skill's own `🏷️ Rename it if the name misleads in your repo` banner already recommends this name, and it is what an adopter calls the job. Once this repo has no upstream, the shipped name describes a relationship that exists nowhere — so the banner and the bidirectional framing both go with it: with no upstream there is no direction left to relativize.

Rename the directory, then the pointers the banner itself lists: every `@.claude/skills/sync-upstream/SKILL.md` reference, the `CLAUDE.md` index entry, and `ADOPTING.md`'s citations (lines 55, 195, 283, 327, 463).

## 3 — Remove `upstream.json`

It names a repo this one does not sync from and an `adopted` set that describes nothing. A stub's watermark is the adopter's to write, which the banner can say directly.

The alternative is a placeholder with an empty `repo`, keeping a path for the catalog to name while describing nothing. Removal reads better from here, but it is your call on your own repo — hence stating the preference rather than deciding it.

## 4 — Catalog consequences

- The `/sync-upstream` row moves from **G0 — The sync path** to **G6 — Stack stubs**, disposition `adopt only if hydrating now`.
- G0's prose ("Adopting this group is what makes every later change at the source reachable. Skipping it leaves you with a snapshot.") is the group's whole rationale and the row was its whole content — so G0 either goes or is rewritten around what remains.
- The `.claude/skills/sync-upstream/upstream.json` row (disposition **rewrite**) goes with the file.
- Assertions 2–3 check that the catalog covers the inventory, so the row has to move rather than simply be deleted.
