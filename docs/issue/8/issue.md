## Context

The repo this boilerplate's infrastructure came from — `Playgramai/playgramapp`,
per `.claude/skills/sync-upstream/upstream.json` — carries
`.claude/skills/bootstrap-workflow-dispatch/SKILL.md`. It was never adopted here:
it has no row in `docs/catalog.md` and no directory under `.claude/skills/`.

Reported by the operator during review of #7, who notes it has been useful for
dispatching arbitrary GitHub Actions workflows, not only test workflows.

## Why it's worth having

`/test-on-gh` is the only dispatch-shaped skill in the catalog today, and it is a
**G6 stub** — it ships as the shape of the job with no procedure, and it is
scoped to test buckets by design. A general "dispatch this workflow against this
branch and report back" routine is a different job with a different audience: it
does not presuppose a test-bucket split, so unlike `/test-on-gh` it may well be
adoptable without hydration.

## What needs to happen

1. Read the skill from a `/sync-upstream` clone of the donor (it is private, so
   this needs a session scoped to it — the file cannot be read from here).
2. Judge how stack-bound it is. If it is generic over `gh workflow run` +
   run-polling, it can be adopted close to as-is; if it names the donor's
   workflows, it needs translating, or splitting into a generic core plus a
   hydration banner.
3. Decide its group. G5 (CI & landing) is the likely home; it would be the first
   non-stub member of that group besides `/watch-ci`.
4. Add its `docs/catalog.md` row — `scripts/check-skill-catalog.sh` assertion 2
   fails without one, which is the intended forcing function.
5. Resolve its closure: whatever it `@`-references travels with it, and if it
   overlaps `/watch-ci`, say in both which one to reach for.

## Acceptance criteria

- [ ] The skill exists at `.claude/skills/bootstrap-workflow-dispatch/` (or a

- [ ] It has exactly one row in `docs/catalog.md` under a stated group.
- [ ] `bash scripts/check-skill-catalog.sh` exits 0 — including assertion 4, so
