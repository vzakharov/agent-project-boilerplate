## Body

## Context

This repo has `scripts/export-github-issue.py`: stdlib-only Python 3.9+, exports
**issues only** — body, comments, timeline and attachments into
`docs/issue/<n>/`. A PR number is not a supported argument.

The donor repo (`Playgramai/playgramapp`, per `upstream.json`) has since replaced
it with `scripts/export-github-item.ts`, which handles **PRs as well as issues**.
Raised by the operator while reviewing #7's catalog row, asking whether the row
was a misnomer or a missed sync. It is a missed sync: the row accurately
describes the file that is here.

## The wrinkle that makes this a port, not a copy

The donor's version is TypeScript, so running it needs a Node toolchain. This
boilerplate is deliberately language-agnostic — the two scripts it ships in a
language at all are stdlib-only Python precisely so a Rust or Go project can use
them without installing anything. Taking the donor's file verbatim would make a
Node install a prerequisite of G3 for every adopter.

So this is a **translate** in `/sync-upstream`'s vocabulary: port the PR-handling
capability into the existing Python script, keeping it stdlib-only, rather than
adopting the donor's implementation.

## What needs to happen

1. Read `scripts/export-github-item.ts` from a donor clone to see what PR support
   actually covers — review threads, review comments and diff hunks are the parts
   with no issue equivalent, and are where the real work is.
2. Extend `export-github-issue.py` to accept a PR number/URL, writing to a path
   that does not collide with the issue tree (`docs/pr/<n>/` is already taken by
   `scripts/pr-body.py`, so this needs deciding rather than assuming).
3. Rename to `export-github-item.py` once it handles both, and update every
   reference: `/issue`'s skill body, the `docs/catalog.md` G3 row, and
   `upstream.json`'s `adopted` list if it names the file rather than `scripts/`.
4. Check whether `/issue` should accept a PR argument as a result, or whether
   that stays out of scope and only the script grows the capability.

## Acceptance criteria

- [ ] One script exports both issues and PRs, still stdlib-only, still 3.9+.
- [ ] The `docs/catalog.md` row's "Requires" column is unchanged — no new
      toolchain dependency reaches an adopter.
- [ ] Output paths for issues and PRs are distinct and documented, and
      `/finalize`'s sweep covers both.
- [ ] `bash scripts/check-skill-catalog.sh` exits 0 after the rename.
