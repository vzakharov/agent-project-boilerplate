## Body

`docs/catalog.md` files `scripts/lib/watch-tick-common.sh` under **G5 — CI & landing**:

| Item | What it does | Requires | Pulls in | Disposition |
| --- | --- | --- | --- | --- |
| `scripts/lib/watch-tick-common.sh` | Shared shell helpers for the watch-tick scripts. | `bash` | — | adopt |

But `scripts/check-merge.sh` — which is **G2**, and which `/check-merge` runs, and which `/finalize` and `/sync-branch` both reach through `/check-merge` — sources it:

```bash
# scripts/check-merge.sh:39
source "${REPO_ROOT}/scripts/lib/watch-tick-common.sh"
```

So an adopter who takes G2 and declines G5 — the documented normal case for a repo with no CI — deletes a file the PR loop needs, and `/check-merge`, `/finalize` and `/sync-branch` all stop working.

## What this is not

**Not a systemic blind spot.** The catalog already declares cross-group script dependencies: G3's `scripts/export-github-item.py` row lists `scripts/lib/github.py (G2)` in its **Requires** column, explicitly group-tagged. Of the script-to-script dependencies in the tree, that is the only other cross-group one, and it is declared. The mechanism works; this row simply does not use it.

**And not silent.** `scripts/check-skill-catalog.sh` greps `@.claude/skills/…` references only, so no script-to-script dependency is machine-checked in either language — but a missing `source` target fails immediately and by name, so the "this failure is silent" framing does not apply here. What earns the fix is *what* breaks and how it reads: the adopter's `/finalize` stops working, which looks like a broken loop rather than an adoption mistake they made three steps earlier.

## Suggested fix

**Move the row into G2** rather than declaring the dependency from G5. The file is needed by one G2 script and one G5 script; the groups partition the inventory, so it can only live in one, and G2 is the group that cannot do without it. Then `scripts/ci-watch-tick.sh`'s G5 row cites it as a G2 requirement — exactly the form `export-github-item.py`'s row already uses.

Found while de-templating a fresh fork by hand: the group-as-catalogued would have broken the loop, so the file was kept against its row.
