## Body

## The gap

`export-github-item.py` and `pr-body.py` reach `api.github.com` through a bare
`urllib.request.urlopen`, which honors `HTTPS_PROXY`. In a web/remote session
where the agent proxy refuses `api.github.com` outright, both scripts fail on
their first call — the export never starts, and `/pr` cannot write a PR body.

Probed from such a session:

```
proxied,  no auth  → 403
proxied,  +token   → 403  {"message":"GitHub access is not enabled for this session.
                            An org admin must connect the Claude GitHub App for this
                            organization.", ...}
direct,   +token   → 200
```

The refusal is not about the URL shape and not about the token: the proxy
declines every `api.github.com` request from a client it did not configure
itself. A direct connection with the same token succeeds.

## Why it hasn't surfaced here

Where the proxy *does* admit `api.github.com`, the only thing it rejects is the
`repositories/{id}/…` shape GitHub puts in `Link` headers — which
`api_paginated` already works around by paginating with an explicit `page=`.
That workaround is evidence the surrounding calls were getting through; the
blanket refusal is a different condition, set per session/org rather than per
URL.

`gh` escapes it only because `.claude/hooks/session-start.sh` shims the binary
to run under `env -u HTTPS_PROXY`. The two Python scripts have no equivalent, so
the shim that makes the whole `gh`-based loop proxy-safe leaves them exposed —
including `/from-branch`, which cites `export-github-item.py` for PR exports, and
`/pr`, which writes bodies through `pr-body.py`.

Related but distinct: #6 covered the `gh` call sites and the GraphQL block. This
is the stdlib-Python half, which no shim reaches.

## The fix

The machinery already exists in this repo — it is just scoped to attachments.
`export-github-item.py` carries `_openers()`, the proxy-then-direct ladder added
in #17, and `download_asset` walks it. The API calls do not.

- Move `_DropAuthOnHostChange`, `_host` and `_openers()` out of
  `export-github-item.py` into `scripts/lib/github.py` as `openers()`, alongside
  the plumbing #18 already shared.
- Route `api_json` (export) and `api()` (pr-body) through that ladder.
- Build a **fresh `Request` per attempt**: `ProxyHandler` calls `set_proxy()` on
  the request object it is handed, so one reused across the ladder still aims at
  the proxy and every later route fails identically to the first. This is the
  non-obvious part and is worth a comment at both call sites.
- Accumulate every route's failure instead of raising the last one — the same
  discipline #22 established for attachments. The pair is what identifies which
  route is closed: "403 from the proxy, then a real 404" reads very differently
  from either half alone, and reporting only the last attempt names a symptom of
  whichever route happened to be tried last.

Keeping the proxy-honoring opener first means an environment where the proxy is
the only route out still works, so this is additive — no environment that works
today changes behavior.

## Acceptance

- In a session where the proxy refuses `api.github.com`, `export-github-item.py
  <n>` writes the export and `pr-body.py` updates a PR body.
- In a session where the proxy serves it, both still take the proxy route.
- When both routes fail, the error names both attempts, in order.

## Provenance

This is running downstream in `vzakharov/life` (private), which hit the blanket
refusal and re-implemented the above against this repo's version of the scripts.
Reported here so the fix lives at the source rather than as a permanent
divergence in the adopter's watermark.
