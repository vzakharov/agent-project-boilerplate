## Body

An adopting project routinely has **human readers in one language and an agent-facing instruction set in another** — the people who approve the work read one thing, the files that steer the agent are written in the language its tooling is written in. Nothing upstream tells an adopting repo to decide this, so the decision gets made implicitly, one file at a time, by whichever session happened to write that file.

The boilerplate already has a shape for exactly this class of thing: the stub skills and `scripts/vet.sh` ship deliberately unhydrated, and the adopter fills them in as a stated decision. **Language belongs in that set.** It is not a default the boilerplate can pick — a monolingual English team's correct answer is "no decision needed" and that is fine — but it is a decision an adopter must be prompted to make explicitly rather than discover halfway through a review.

### What the decision has to cover

The surface is wider than "which language are the docs in", and every adopter that has drifted has drifted by missing one of these:

- **Durable docs** — `README.md` and whatever else a human reads to decide something, versus `CLAUDE.md`, `.claude/skills/**` and `.claude/rules/**`.
- **Transient working artifacts** — `docs/plans/`, issue exports. These split from durable docs rather than following them: they are swept before merge and read while they live by the session working against them, which argues for the agent's language even where the durable docs are not in it.
- **Commit and PR text** — commit messages, PR titles and bodies. These are `git log` and review surface, so they follow the human side.
- **Skill-emitted prose** — the bodies `/pr`, `/squash-message` and `/qa-checklist` write.
- **Conversation** — issue and PR comments, review replies, session replies. Worth calling out separately, because the natural rule here is different from all of the above: an exchange follows the language it was asked in rather than being fixed to one, since it is not a standing artifact.
- **Code** — comments, docstrings, identifiers.

### The constraint that holds regardless of the answer

**A marker another skill matches on literally stays English**, whatever the surrounding prose is. Today that is at least the `## Summary` and `## QA Checklist` headings that `/qa-checklist` locates by text, the `Proposed squash title/body:` lead that `/squash-message` Step 4 locates the same way, and the semantic commit prefixes. Translating one of these does not produce a translated section — it produces a *second* section beside the one the skill could not find. This is the part that is genuinely upstream's to state, because it is a property of how the skills are written, not of any adopter's choice.

### A worked example, not the answer

`vzakharov/ai-bookkeeper` (an adopter) has a `## Language` section in its `CLAUDE.md` splitting Russian human-facing prose from English agent-facing prose, with the transient-artifact and conversation carve-outs above. Cite it as one filled-in instance if that helps the hydration prompt; the boilerplate should not carry the split itself, or it stops being a decision.

### Related: #53

Filing a non-ASCII convention immediately hits #53 — `check-squash-message.sh` measures with `${#line}`, which counts bytes, so the 80-column title and 72-column body caps roughly halve for any non-Latin script and `vet.sh` rejects a correctly wrapped message. Still open and still byte-counting on `main` (`scripts/check-squash-message.sh:196-228`). The two are separable, but any adopter that answers this hydration prompt with a non-Latin script is blocked by #53 on its first `/finalize`, so it is worth landing first.
