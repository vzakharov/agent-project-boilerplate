## Body

## Context

Raised by the operator reviewing #7. That PR added, to `README.md` and
`docs/catalog.md`, the point that `/plan` and `/implement` outgrew the bug that
prompted them:

> And the bug is no longer the point — a plan on disk is reviewable from another
> machine, holds a **DRY notes** section the operator can argue with before any
> code exists, and ends by handing over a copy-pasteable `/implement <branch>`
> line that starts the next session with the approval already recorded. Native
> plan mode gives none of that even where it works correctly.

That belongs in the skills themselves, durably. Kept out of #7 deliberately to
avoid overloading it.

## Why it matters more than a docs tidy-up

**`README.md` and `docs/catalog.md` are both `never` rows** — they are never
copied into an adopting repo. So today the *only* statement of why these skills
are worth having lives in two files an adopter will never possess. What does
travel is `/plan`'s own framing, which is bug-first throughout:

- Its frontmatter: *"for web/remote sessions where those UIs are buggy"*.
- Its first section, "Why this skill exists", is entirely about the re-emitted
  prompts and links the tracking issue.

An adopter reading that reasonably concludes two things, both wrong: that the
skill is dead weight in a local-only repo, and that it becomes dead weight the
day [anthropics/claude-code#72704](https://github.com/anthropics/claude-code/issues/72704)
is fixed. The catalog's closure note says the opposite — `/plan` travels with G2
even for a local-only adopter, because `/implement`, `/finalize`,
`/propose-issue` and `/audit-github-backlog` all reference it — but again, the
catalog does not travel.

## What needs to happen

1. Rewrite `/plan`'s "Why this skill exists" so the bug is the *origin* rather
   than the *justification*, and state the durable value: a reviewable artifact
   on disk, the `## DRY notes` section forcing the reuse-vs-duplication call
   before implementation, the filename as approval gate, and the
   `/implement <branch>` handoff that carries approval into a fresh session.
2. Reword the frontmatter `description` so it doesn't read as conditional on a
   bug. It is what the operator scans in the skills list and what an invocation
   matches against, so it is a separate surface from the body — the same
   two-surface problem `check-skill-catalog.sh` assertion 4 exists for.
3. Give `/implement` the matching one-liner: what it assumes about approval and
   why the flip is on-record, rather than leaving that inferable only from
   `/plan`.
4. Keep it non-duplicative. `README.md` and `docs/catalog.md` already say this
   for *this* repo's reader; the skills should carry the version an adopter
   needs, not a third copy. Worth a `/dry` pass across the three.

## Acceptance criteria

- [ ] A reader who has only `.claude/skills/` — no README, no catalog — can tell
      why `/plan` is worth keeping in a repo where native plan mode works.
- [ ] Neither the body nor the frontmatter implies the skill retires when the
      upstream bug is fixed.
- [ ] The tracking-issue link survives as history, not as the rationale.
- [ ] No third copy of the argument: the three sites say it once each, for their
      own audience.
