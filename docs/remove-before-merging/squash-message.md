```
scripts/export-github-item.py could not download any attachment on
github.com/user-attachments/..., which is where GitHub has served
every issue-composer upload since 2024. /issue therefore proceeded
without the screenshots and recordings the exporter exists to fetch,
and near-silently: a failed download printed one stderr line while
the export still reported success.

Two independent causes had to land together, since fixing either
alone leaves the exporter broken in one environment. Those URLs
redirect to a pre-signed S3 URL and urllib re-sends every header
across a redirect, so S3 saw both its query signature and a bearer
token and answered 400 InvalidArgument; a redirect handler now
strips Authorization when the host changes, leaving a same-host
redirect that still needs the token alone. Separately the
remote-session egress proxy refuses that path outright with 403
before GitHub is reached, so asset downloads retry on a
proxy-bypassing opener, the same accommodation the session-start
hook already makes for gh. The proxy-honoring attempt stays first,
so an environment where the proxy is the only egress route is
unaffected.

A single-attempt error message is what disguised the first cause as
the second, so failures now report both attempts -- still without
the response body, which echoes the offending header value, i.e. the
bearer token in full. The API paths keep going through the proxy
unchanged, talking to api.github.com on repository-scoped paths it
permits, and the opener is an optional parameter on the shared
request helper rather than a second copy of it. The patch is
deliberately identical to its copy in vzakharov/vovazakharov.com, a
downstream adopter, so /sync-upstream stays a no-op on this file.

Fixes #17
```
